平台服务端对接文档

提供给第三方发行平台的协议，覆盖支付成功通知、用户核验，以及接收游戏事件转发。

纯 HTML · 无外部依赖基于当前 main 协议整理6 个章节

平台对接准备

中台对平台开放的请求与中台主动上报接口

平台与中台对接主要有三项：支付成功回调、主动发起用户核验、接收中台上报事件。用户核验由独立 SDK Service 处理，支付回调和事件转发由 SDK Core 处理。

参数说明
envprod 正式、test 测试、review 提审
appid渠道包的全局唯一编码，例如 110006
gameSecret游戏侧与中台共用签名密钥；仅服务端保存
appSecret平台与中台共用签名密钥；由中台维护，游戏侧不使用

双方需要确认

  • 平台分配的 AppID 及对应 appSecret；渠道包在中台配置中维护相同密钥。
  • 支付回调地址 /api/core/pay/notify/{appid}，不包含 env。
  • 用户核验按环境分别提供 /api/service/user/check/{env}，环境值由双方约定。
  • 平台的事件接收完整 URL，由中台配置 platform.eventReportURL。
  • 平台回调采用自己的原生 SHA-1 协议，不能和游戏侧请求签名混用。
用户核验签名当前实现包含 open_id，但平台原文档未单独明确该字段；正式接入前必须核对一组真实签名样本。

支付成功回调

平台支付成功后通知 SDK Core
POST/api/core/pay/notify/{appid}

平台向中台发送支付成功通知，Core 校验签名和已登记的游戏订单，确认后由中台异步通知游戏发货。平台不需要直接调用游戏服。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
order_nostring是平台订单号
game_order_idstring是游戏订单号
amountinteger是实付金额，单位分
attachstring是游戏登记透传参数，无内容传空字符串
paid_atstring是支付完成时间

请求示例

HTTP
POST /api/core/pay/notify/110006 HTTP/1.1
Host: api.example.com
Content-Type: application/json
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 appSecret 生成的 V1 签名>

{"order_no":"P100","game_order_id":"G100","amount":600,"attach":"roleId=1","paid_at":"2026-11-03T00:00:00Z"}

成功响应

HTTP
HTTP/1.1 200 OK
Content-Type: text/plain

0123456789abcdef

平台原生 V1 验签

  • 参与签名：order_no、game_order_id、appSecret、Header 的 x-nonce 与 x-timestamp。
  • 将这五个值转字符串、按字典序升序排序，以 _ 拼接后 SHA-1，输出小写 40 位 hex。
  • amount、attach、paid_at 不参与平台 V1 签名；中台会核对订单金额与 attach，但不额外向平台查单。
  • 仅 HTTP 200 且响应体精确等于请求 nonce 才算 Core 已确认接收；其他情况平台按其重试策略处理。
回调 URL 无 env，Header 的 x-app-id 并非本回调签名的必需字段；AppID 由 URL 给出。请勿把游戏侧的“Body 顶层全部值参与签名”规则套用到此处。

用户核验

平台验证 open_id 对应的游戏用户是否存在
POST/api/service/user/check/{env}

平台请求 SDK Service，由 Service 根据渠道包、环境和中台配置找到游戏对应的核验地址，调用游戏并将结果转换为平台约定的格式。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
open_idstring是登录后获取的平台用户标识

请求示例

HTTP
POST /api/service/user/check/test HTTP/1.1
Host: api.example.com
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 appSecret 计算的 SHA-1 小写签名>

{"open_id":"user123"}

用户存在

JSON
{
  "code": 0,
  "message": "ok",
  "data": true
}

用户不存在

JSON
{
  "code": 1021003,
  "message": "用户信息不存在",
  "data": null
}
  • env 仅可为 prod/test/review；AppID 由 x-app-id 提供。
  • 需要启用 user_check 的全局和对应渠道环境开关；无绑定默认关闭。
  • 当前 Service 按 appSecret、AppID、timestamp、nonce、open_id 五个值参与 SHA-1 签名校验。
  • 游戏请求失败不应被解释成“用户不存在”：超时、网络故障和错误响应分别处理。
待平台联调确认：平台原文档未明确用户核验是否签 open_id，以及同一 AppID 能否分别配置 prod/test/review 回调地址。未确认前不应开放正式流量。

接收事件上报

Core 同步转发游戏的渠道包事件
POST{platform.eventReportURL}

游戏向 SDK Core 上报事件，通过双层功能开关和游戏验签后，Core 将 event 与 ext 原样传给平台。平台只需要提供事件接收地址，不需要向 Core 反向推送此类事件。

请求地址

POST {platform.eventReportURL}。例如测试地址为 https://openapiv3.qk6.top/report/event；正式地址请按实际环境约定。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
eventstring是事件名
extobject是渠道协议对应的业务数据对象

请求示例

HTTP
POST /report/event HTTP/1.1
Host: openapiv3.qk6.top
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 appSecret 计算的 SHA-1 小写签名>

{"event":"login","ext":{"areaId":"1","openId":"user123","roleId":"45940775","roleLevel":80}}

平台成功响应

JSON
{
  "code": 0,
  "message": "ok",
  "data": true
}
  • 平台入站验签只使用 appSecret、x-app-id、x-timestamp、x-nonce，Body 不参与签名。
  • 中台要求平台返回 HTTP 200、code=0 且 data=true，才把本次转发视为成功。
  • Core 对平台请求超时为 5 秒、不跟随重定向；当前不保存事件、不自动重试。
  • 不同渠道的 event/ext 业务含义由平台的渠道协议约定，中台不修改字段名或结构。
这是中台主动转发平台的接口，不是第三方平台调用中台的接口。

签名算法对照

三种平台交互采用不同的参与字段
调用方向签名参与值Body 参与情况
平台 → Core：支付回调appSecret、order_no、game_order_id、nonce、timestamp只使用两个指定订单字段
平台 → Service：用户核验appSecret、appid、timestamp、nonce、open_id当前实现包含 open_id；待联调确认
Core → 平台：事件上报appSecret、appid、timestamp、nonce不包含 Body

统一计算步骤

  • 把参与值全部按字符串处理（空值按接口协议过滤）。
  • 按字符串值字典序升序排序；用 _ 拼接。
  • 对 UTF-8 拼接结果计算 SHA-1，输出 40 位小写十六进制。
  • 平台交易密钥 appSecret 只保存在平台与中台的可信服务端，不下发给游戏客户端。

伪代码

Text
values = [本接口定义的参与值...]
plain = values.filter(非空).map(String).sort().join("_")
x-signature = lower_hex(sha1(UTF8(plain)))
请勿只根据“同样是 SHA-1”判断协议相同；签名字段集合不同，会直接导致 401。平台出站用户核验还需用真实向量锁定。

响应与联调检查

平台对接常见状态及验收条件
HTTP 状态一般含义
400请求格式、字段或路径参数不合法
401签名或鉴权失败
403功能未启用或无权访问
404AppID 不存在、环境未绑定或路由无效
409订单重复登记但参数不一致等业务冲突
422密钥或业务配置不合法（适用于部分接口）
502/504调用上游失败或超时
503依赖服务或必要配置不可用

推荐联调清单

  • 支付回调：验签正确、错误签名、未知订单、金额不一致、重复回调、精确 nonce 应答。
  • 用户核验：存在/不存在、功能关闭、目标环境未绑定、游戏上游超时；先确认真实签名样本。
  • 事件接收：平台按 Header 验签、不把 Body 加入签名；正常返回 {code:0,data:true}。
  • 检查两端时间同步与 nonce 格式，确认 HTTP 失败后的重试和幂等策略。
中台内部管理 API、配置同步 API 不属于平台的公开对接范围。
