DEVELOPER GUIDE / ARCHITECTURE

服务职责、数据流、配置同步与安全边界

研发中台架构（当前实现）

本文仅描述当前系统结构；具体表结构见 数据库文档，接口与签名规范见 统一接口文档。

服务与数据流

text
Vue 3 管理端 ──HTTP──> config-center ────────> 权威 MySQL（config_center）
                             │                         ↑
                    节点变更写入 revision              │ 只读 JOIN
                             │                         │
                             └──签名 Webhook──> config-center-access
                                                   │          │
                                            HTTP 拉取节点     本地 MySQL
                                            快照/增量日志     （config_access）

游戏/客户端 ──SDK 配置、订单─────────> sdk-core ───> 权威 MySQL
平台 ──支付回调──────────────────────> sdk-core ───> 游戏发货通知
平台 ──核验、查询、封解禁──────────────> sdk-service ──适配器──> 游戏接口
游戏 ──事件上报、订阅消息──────────────> sdk-service ───────────> 平台
                                               └──────────────> 权威 MySQL（只读）
  • config-center：管理基础节点与订阅者，并提供同步版本、变更记录、快照查询。
  • config-center-access：可选独立接入服务，缓存三级节点，不存储渠道应用，也不向权威库写入。
  • sdk-core：直接查询权威库，根据环境绑定和接口映射生成配置；管理订单、支付回调、异步发货以及 SDK 专属配置、渠道包和功能开关。
  • sdk-service：平台主动调用游戏，处理平台发起的用户核验、角色/区服查询、封解禁，以及游戏上报的事件和订阅消息；游戏侧调用支持默认和定制适配器，业务数据不在此服务落库。
  • config-center-admin：Vue 3 管理界面，管理接口默认启用 adminAuth 签名校验，生产仍须配置 TLS 与受保护的管理网关。

配置数据模型

config_node 只有三种节点：

  1. game：根节点，game_id 与 region_id 均为空。
  2. region：归属于游戏，env_type 仅支持 test、prod、review（旧数据可能为空）。
  3. server_group：归属于游戏与大区。

表不再使用 parent_id；接口的 parentId 由 game_id / region_id 推导。sdk_channel_app 是独立表，code 全局唯一，每个 AppID 的 prod_server_group_id、test_server_group_id、review_server_group_id 各指向至多一个区服组。三个环境共享同一份应用 config JSON，不存在独立绑定配置表，也不自动向上继承 JSON。

节点变更与同步一致性

  1. 配置中心写入三级节点时，在同一 MySQL 事务中更新节点、全局 revision 和 config_node_change_log，确保版本提交次序一致；无变化写入不增加 revision。
  2. Webhook 仅携带 epoch、revision，使用订阅者密钥参与 SHA-1 排序签名，并校验时间窗口和 nonce，不在通知内传输完整配置。接入端收到有效通知后异步拉取。
  3. 接入端按 revision 获取变更节点 ID，再批量查询最新节点；节点内容与游标在本地同一事务提交。初始化、epoch 变化或变更日志断档时使用一致性快照。
  4. 接入端定时校对版本（默认 5 分钟）补偿丢失的 Webhook；HTTP 202 表示通知已受理，不等于节点已完成同步。
  5. sdk_channel_app 的增删改及三环境绑定不推进三级节点的 revision，SDK Core 直接从权威库读取，不依赖接入副本同步。

配置中心多实例可共享权威 MySQL；投递进度由数据库租约与重试协调。单个 MySQL 仍是单点，生产需要独立的备份与故障恢复机制。

边界与演进原则

  • 当前数据库由管理员手动执行 SQL 建表或升级；各服务启动只校验表结构，不执行 DDL、也不维护历史迁移版本。
  • 服务内部业务路由不包含 /sdk 或 /v1；Nginx 可分别转发 /api/config/、/api/core/、/api/service/，公网若使用 /sdk/ 前缀由网关负责转换。
  • 接口级字段映射编译进 sdk-core，新增映射字段不必修改 SQL，但需要重新构建并滚动部署。
  • 管理接口默认使用 adminAuth 签名，仍须通过可信内网或受保护的 HTTPS 网关访问；同步接口和回调地址也需限制访问。生产环境不能将管理 API 与公开 SDK API 无差别暴露。

部署方案见 生产运维。

SDK 业务与密钥边界

  • sdk_service 管理已实现功能的全局开关，sdk_service_channel 按服务、渠道包、环境唯一绑定；当前功能包括 event_report、subscribe_message、user_check、role_query、server_query 和 role_control。
  • 游戏侧用 sdk_node_config(game).config.gameSecret 验签，平台侧用 sdk_channel_app.config.appSecret 验签；两套签名密钥不能混用。
  • 订单登记与支付回调具有持久化处理和异步发货补偿，游戏必须幂等；渠道事件目前同步转发、不入库、不自动重试；用户核验不缓存、不落库、不自动重试。
  • 对外协议及签名细节以 游戏 HTML 和 平台 HTML 为准，避免维护多份相同字段表。

SDK Core 与 SDK Service 职责

  • sdk-core：管理 SDK 节点配置、渠道包、服务开关，并承担配置查询、订单登记、支付回调和游戏发货通知。
  • sdk-service：承担平台 → 游戏的核验/查询/封解禁，以及游戏 → 平台的事件上报/订阅消息推送。
  • 事件上报迁移后统一入口为 POST /api/service/events/{env}，订阅消息为 POST /api/service/subscribe/{env}；不保留 Core 旧事件入口。
  • 两类平台上报均沿用 sdk_service 全局开关和 sdk_service_channel 渠道环境开关，无新建业务数据表。

统一 SDK 节点配置

config_node 继续保存游戏、大区和区服组的基础信息与 JSON；SDK Core 独立管理 sdk_node_config(node_id,config)，同一节点最多一条 SDK 配置。SDK 密钥、适配器、游戏回调地址不再属于配置中心同步数据。渠道包由 sdk_channel_app 管理；SDK Service 直接只读 JOIN SDK 配置表，无须经 Core HTTP 查询。

在共享 MySQL 中，Node 与 SDK 配置存在跨模块外键依赖。旧库迁移、服务同步切换及清理旧 JSON 分开执行，参见 数据库文档。

内部路由与健康检查

  • 业务接口、管理接口、请求字段与签名规则统一维护于 接口文档；本文件不重复完整 HTTP 契约。
  • 配置中心的节点读取与同步内部入口包括 GET /api/config/nodes/{id}、POST /api/config/nodes/batch-get、GET /api/config/sync/revision、GET /api/config/sync/changes、GET /api/config/sync/snapshot。
  • 接入端提供 GET /api/access/nodes、GET /api/access/revision，通过 POST /internal/config/callback 接受 Webhook 后异步同步。
  • 各 Go 服务提供 GET /health/live（进程存活）和 GET /health/ready（依赖就绪）；本地验证方式见 开发指南，生产探针见 运维指南。
DEVELOPER GUIDE / DATABASE

数据模型、全量 SQL、增量升级与迁移

数据库结构与手动 SQL

核心约定

所有建表和升级都由管理员人工执行 SQL。 四个 Go 服务不会在启动时执行 DDL；只校验实际表结构。SQL 随 Linux 发布包一起交付，也可从源码中获取：

场景手工执行的 SQL
新建空的 config_centerconfig_center.sql
新建空的 config_accessconfig_access.sql
已有库缺少订单表V0001__add_game_order.sql
已有库缺少 SDK 服务表V0002__add_sdk_services.sql
旧通用服务绑定表迁移（特定旧结构）V0003__migrate_sdk_service_channel.sql
已有服务表缺少核验用户信息目录V0004__add_sdk_user_check.sql
已有服务表缺少角色查询目录V0005__add_sdk_role_query.sql
已有服务表缺少区服查询目录V0006__add_sdk_server_query.sql
已有服务表缺少封禁与解禁目录V0007__add_sdk_role_control.sql
已有服务表缺少订阅消息目录V0008__add_sdk_subscribe_message.sql
旧版本 SDK 专属配置迁移（需停服备份）V0009__migrate_sdk_node_config.sql
SDK 迁移验证完成后的旧字段清理V0010__cleanup_legacy_sdk_fields.sql
已有游戏节点缺少运营地区字段V0011__add_game_market_type.sql

不得对已有配置数据的库再次执行 db/full/ 中的全量 SQL。执行前备份，确认 MySQL 8.0+、目标库名称、当前表结构及 SQL 内容。初始化 SQL 不包含 DROP TABLE。已有库应先核对当前表定义、备份及 SQL 内容，切勿在结构不明的库上盲目执行初始化或增量 SQL。

SQL 目录与增量编号

  • 根目录 db/full/：config_center.sql 与 config_access.sql 是当前完整结构快照，仅用于新建对应空库，不包含生产业务数据。
  • 根目录 db/incremental/：文件命名为 V0001__description.sql，序号全局连续递增，历史存量脚本为 V0001～V0011；下一份增量是 V0012。跨数据库时在文件名中注明 config_center 或 config_access。
  • 新增数据库变更时，创建新编号的增量 SQL，并同步更新对应的全量 SQL，以及本文和 CI、发布相关检查。已经发布的增量 SQL 不允许修改、删除或重新编号。
  • 新增增量 SQL 头部注明目标数据库、适用旧结构与前置条件；所有 SQL 仍由管理员手工检查并执行。
  • 注意：V0001～V0011 是不同历史版本、不同场景的 SQL 归档编号，并非可全部连续执行的升级链。 例如 V0003 只适用于仍有旧 sdk_service_binding / scope_type 的库，V0009 仅适用于旧渠道表结构。已升级的库不得重跑。
  • 当前不引入 Flyway、自动执行或迁移版本记录表。编号本身不能证明数据库已经应用过该变更，执行前需检查真实表结构、数据和历史操作记录。

源码目录 db/full/、db/incremental/ 在发布包中分别对应 sql/full/、sql/incremental/。原有 config-center/internal/sqlc/ SQL 仅用于代码生成，不属于手动数据库部署脚本。

本地 MySQL 示例

sql
CREATE DATABASE IF NOT EXISTS config_center
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS config_access
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

只对新建空库执行初始化：

bat
mysql -u root -p config_center < db/full/config_center.sql
mysql -u root -p config_access < db/full/config_access.sql

上面两行采用 shell 输入重定向，适用于 CMD/bash；PowerShell 可直接在 Navicat、DataGrip 等数据库工具中执行 SQL，或从 CMD 调用。

已有 config_center 库且缺少订单表时，只执行：

sql
-- 先核对订单表是否已存在
SHOW TABLES FROM config_center LIKE 'game_order';

检查后在数据库工具中运行 db/incremental/V0001__add_game_order.sql。该 SQL 只创建 game_order，不会改动配置表及历史业务数据。若表已经存在，不要重复运行，应先对比字段、索引和数据。

执行后核对：

sql
SHOW TABLES FROM config_center LIKE 'game_order';
SHOW CREATE TABLE config_center.game_order;
SELECT COUNT(*) FROM config_center.config_node;

权威库的业务表

  • config_node：游戏、大区、区服组三级节点；region.env_type 为 prod/test/review
  • sdk_channel_app：SDK Core 管理，全局唯一 AppID、共享 JSON 配置、三环境绑定
  • sdk_node_config：SDK Core 管理，node_id 引用 config_node.id，游戏/大区/区服组的 SDK 专属 JSON
  • config_revision、config_node_change_log：同步游标和变更日志
  • config_subscriber、config_subscriber_delivery_state：Webhook 订阅者和投递状态
  • game_order：SDK Core 充值订单、支付状态、通知租约和补偿
  • sdk_service：SDK 功能目录与全局开关，新库初始化预置已实现的 event_report、subscribe_message、user_check、role_query、server_query、role_control，不包含 scope_type、sort_order
  • sdk_service_channel：按 service_id + channel_app_id + env 唯一的渠道包服务绑定

config_center 的配置表与订单表使用同一个数据库。SDK Core 只使用一个 database.dsn 连接池；建议配置表只授予 SELECT、订单表授予 SELECT/INSERT/UPDATE，运行账号不授予 DDL。

SDK 功能配置与数据安全

  • sdk_service_channel 使用 (service_id, channel_app_id, env) 唯一约束，env 只能是 prod/test/review。
  • event_report、subscribe_message、user_check、role_query、server_query 与 role_control 均要求服务全局开关、渠道包环境开关同时启用；无渠道环境绑定即默认关闭。
  • sdk_service_channel.config 为 JSON 对象；当前事件上报不使用事件级规则，不持久化和自动重试。
  • SDK Core 的管理接口为 GET /api/core/admin/services、PUT /api/core/admin/services/{id} 和渠道包 /api/core/admin/channel-apps/{id}/services 系列，详见 管理接口。
  • 充值订单和发货通知不依赖功能开关。
  • MySQL DDL 会隐式提交，失败时不能假定事务回滚。应检查实际执行到哪一条 SQL，再制定恢复步骤。
  • 接入端副本 config_access 独立于权威库，只保存三级节点及同步游标。首次全量拉取由接入服务在表结构就绪后完成，不再自动建表。
  • 生产环境继续控制 /api/config/** 的访问权限，保护 gameSecret 和其他原始配置密钥。

SDK 配置拆分上线顺序

  1. 在维护窗口停止旧版本 config-center、所有 sdk-core-*、sdk-service 与管理端写操作；备份 config_center 并核对真实字段。
  2. 已有库执行 db/incremental/V0009__migrate_sdk_node_config.sql。该脚本创建 sdk_node_config、复制已知的游戏/大区 SDK 字段，并将 config_channel_app 改名为 sdk_channel_app。保留旧 config_node.config JSON 供比较，禁止对已经迁移的库重复执行。
  3. 对比游戏密钥、适配器、五类回调地址、渠道包数量/ID、环境绑定及功能开关，检查是否存在未归类的自定义 SDK 字段。确认没有遗漏后再升级二进制与前端。
  4. 同时切换 config-center、全部 sdk-core、sdk-service，不能保留混合新旧版本；Nginx 新增对 /api/core/admin/ 的保护。验证配置查询、订单登记/回调/发货、角色与区服查询、封解禁、事件与订阅消息。
  5. 验证通过后，在单独维护窗口人工执行 db/incremental/V0010__cleanup_legacy_sdk_fields.sql。清理后校验配置快照和日志不再包含 SDK 密钥。不得通过自动启动逻辑执行 DDL。

注意：MySQL DDL 隐式提交，迁移脚本不是单事务；重命名表前应确认目标表不存在，失败时人工核对已执行步骤。仅对已知 SDK 字段自动搬迁，未知自定义键需人工识别及处理。密钥迁移不可输出明文到 CI 或审计日志。

DEVELOPER GUIDE / DEVELOPMENT

本地启动、联调测试与 CI

本地开发与联调

本文以 Windows PowerShell 为例；四个 Go 服务使用各自的 configs/config.yaml 作为公开模板，复制为未提交且完整独立的 configs/config-dev.yaml 并填写凭据。启动只读取 -config 指定的单个 YAML，不继承同目录的 config.yaml；环境变量可以覆盖支持的字段。不要将包含真实密码的 YAML 提交 Git。

环境

  • Go 1.27.3、MySQL 8.0+；运行 Vue 管理端另需 Node.js 22 / npm。
  • 本地默认端口：config-center:8080、config-center-access:8081、sdk-core:8082、sdk-service:8221。
  • 权威数据库和接入副本必须分开：config_center 与 config_access。

使用 MySQL 管理工具执行：

sql
CREATE DATABASE IF NOT EXISTS config_center
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS config_access
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

1. 权威配置中心

打开第一个 PowerShell 终端：

powershell
cd config-center
Copy-Item configs/config.yaml configs/config-dev.yaml

修改 configs/config-dev.yaml 中的 database.dsn，例如 root:your-password@tcp(127.0.0.1:3306)/config_center?parseTime=true&loc=UTC。管理读写路由和 Webhook Worker 会在启动时自动注册；管理接口默认启用 adminAuth 签名；下文未携带签名的本地管理请求示例，仅适用于隔离的本地开发环境，需在 config-center 和 sdk-core 的 configs/config-dev.yaml 中显式设置 adminAuth.enabled: false。如保持默认开启，请按 管理签名规范 添加请求头。生产不得免签，并须经受保护的 HTTPS 网关访问；新增订阅者无需重启。回调支持公网/内网的域名与 IP（HTTP/HTTPS），无需配置域名白名单。

对新空库先手动执行 SQL，再启动：

powershell
# 先在数据库工具中执行 db/full/config_center.sql（仅新库）
go run ./cmd/config-center -config configs/config-dev.yaml

成功后检查 http://127.0.0.1:8080/health/ready。若提示数据库表或字段缺失，先核实 DSN、表结构以及 SQL 是否已手工执行；启动程序不会建表。

2. 接入端（可选）

新终端进入 config-center-access：

powershell
cd config-center-access
Copy-Item configs/config.yaml configs/config-dev.yaml
# 修改 YAML 中 database.dsn / configCenter.url / webhook.secret
go run ./cmd/config-center-access -config configs/config-dev.yaml

database.dsn 指向 config_access，configCenter.url 通常是 http://127.0.0.1:8080，webhook.secret 必须是足够长的随机密钥。首次启动前须对空 config_access 执行 db/full/config_access.sql，随后全量拉取节点，随后增量同步；旧副本库参见 数据库文档。

在运行中的配置中心注册订阅者（示例密钥需与接入端一致，且管理写接口必须在受保护的网络上启用）；无需重启 Worker：

powershell
$body = @{
    code = "access-local"
    callbackUrl = "http://127.0.0.1:8081/internal/config/callback"
    secret = "replace-with-a-strong-local-secret"
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8080/api/config/admin/subscribers" -ContentType "application/json" -Body $body

检查 http://127.0.0.1:8081/api/access/revision。Webhook 使用 X-Timestamp、X-Nonce、X-Signature，将订阅者密钥、时间戳、nonce、epoch、revision 按值排序计算 SHA-1。签名验证成功只代表已接受异步同步，真正的节点更新以副本游标和节点结果为准。旧 HMAC-SHA256 接入端不再兼容，新旧服务端必须同步升级。

DEVELOPER GUIDE / PRODUCTION

Supervisor、Nginx、发布流程与排障

生产部署与运维（Supervisor 优先）

部署模型：Linux 二进制 + 独立 MySQL 8.0+ + Nginx + Supervisor。systemd 可选，但本文以当前采用的 Supervisor 为主要方案。服务管理配置不放入仓库，也不包含在发布包中；生产机无需安装 Go、Node.js。

配置中心与 SDK Core 管理 API 默认启用 adminAuth 请求签名，但签名不代替访问控制。管理、同步、接入回调仍须通过可信内网或具备认证、白名单和 TLS 的专用网关暴露。对外开放的业务 API 包括必要的 /api/core/** 与 /api/service/**，其他管理与同步路径仍需保护。

1. 部署目录与端口

text
/data/middle-platform/
├── bin/             # 四个 Linux 可执行程序
├── config/          # 生产 YAML（禁止提交 Git 或打入归档）
├── admin/           # Vue 静态文件
└── logs/            # 由 Supervisor 或系统负责轮转

建议：config-center:8201、sdk-core-1:8211、sdk-core-2:8212、sdk-service:8221、config-center-access:8291（可选），管理端由内部 Nginx 提供。具体端口按现有主机资源调整；不同实例不得占用同一监听地址。

  • config-center 多实例共享 config_center 权威库。
  • sdk-core 使用单一 database.dsn 和单连接池，配置表只读、config_center.game_order 限定读写；订单接口及补偿 Worker 随服务启动。多实例可共用一份 YAML，并通过 SDK_CORE_ADDR 覆盖监听端口。平台 v1 通过签名、订单与金额一致性校验后确认支付；不查单，但签名未覆盖金额的残余风险必须明确接受。
  • config-center-access 只有需要本地三级节点副本时才部署，使用独立 config_access 库。

2. 打包上传与首次安装

在开发机执行：

powershell
.\scripts\package.ps1 -Arch amd64 -Version v1.0.0

将 dist/middle-platform-v1.0.0-linux-amd64.tar.gz 上传到服务器 /tmp/。仅首次部署且确认程序尚未运行时，可用以下命令安装：

bash
sudo mkdir -p /data/middle-platform/{bin,config,admin,logs}
sudo mkdir -p /tmp/middle-platform-stage
sudo tar --no-same-owner -xzpf /tmp/middle-platform-v1.0.0-linux-amd64.tar.gz -C /tmp/middle-platform-stage
file /tmp/middle-platform-stage/bin/*
ls -l /tmp/middle-platform-stage/bin/
sudo cp -a /tmp/middle-platform-stage/bin/. /data/middle-platform/bin/
sudo cp -a /tmp/middle-platform-stage/admin/. /data/middle-platform/admin/

使用 -SkipFrontend 构建的包没有 admin/，不要执行对应 cp。创建低权限服务账号 middle-platform，按实际用户/组授予 bin/、config/ 和 logs/ 最小权限；真实 config-center.yaml、config-center-access.yaml、sdk-core.yaml、sdk-service.yaml 单独放在 /data/middle-platform/config/。

打包参数及产物

scripts/package.ps1 是唯一手动打包入口，支持 Windows PowerShell 与 GitHub Actions 统一生成 Linux ELF + tar.gz。依赖 Go 1.27.3；包含前端时还需要 Node.js 22 / npm。

powershell
.\scripts\package.ps1 -Arch amd64 -Version v1.0.0
.\scripts\package.ps1 -Arch arm64 -Version v1.0.0
.\scripts\package.ps1 -SkipFrontend -Version v1.0.0

省略 -Version 时使用提交号或本地时间作为版本标识；Go 交叉编译加 -buildvcs=false。正常情况下 dist/ 只保留一个版本归档，没有中间目录。

归档结构以打包脚本为准：

text
bin/
  config-center
  config-center-access
  sdk-core
  sdk-service
sql/
  full/
    config_center.sql
    config_access.sql
  incremental/
    V0001__add_game_order.sql
    ...
    V0011__add_game_market_type.sql
admin/                     # -SkipFrontend 时不存在

归档不包含生产密钥、YAML、Nginx/Supervisor 配置。Linux 可执行文件保存 0755 权限，可在上传后执行 tar -tzf、file bin/* 校验。GitHub Actions .github/workflows/package.yml 使用同一脚本并检查 ELF 架构与权限。打包不会自动部署、执行 SQL 或管理 Supervisor。

3. 手动 SQL 先于启动

备份并核对目标数据库，只执行对应场景的 SQL。现有 V0001～V0011 为不同历史场景的编号归档，不可以不经检查而依次执行：

  • SDK 拆分升级：停所有旧实例并备份后执行 sql/incremental/V0009__migrate_sdk_node_config.sql，验证新版后单独执行 sql/incremental/V0010__cleanup_legacy_sdk_fields.sql。详见 数据库文档。
  • 全新、空的 config_center：sql/full/config_center.sql。
  • 已有 config_center 仅缺少订单表：sql/incremental/V0001__add_game_order.sql。
  • 已有权威库但没有 SDK 服务表：sql/incremental/V0002__add_sdk_services.sql（仅表确实不存在时执行）。
  • 已有功能表但缺少 user_check 服务目录：sql/incremental/V0004__add_sdk_user_check.sql。
  • 已有服务表但缺少角色查询、区服查询或封解禁目录：分别手工执行 sql/incremental/V0005__add_sdk_role_query.sql、sql/incremental/V0006__add_sdk_server_query.sql、sql/incremental/V0007__add_sdk_role_control.sql，在部署新版 sdk-service 前完成。
  • 已有服务表但缺少订阅消息目录：手动执行 sql/incremental/V0008__add_sdk_subscribe_message.sql，在部署新版 sdk-service 前完成。
  • 全新、空的 config_access：sql/full/config_access.sql。

例如在 Linux 发布包解压目录（已有库补建订单表）：

bash
mysql -u <管理账号> -p config_center < sql/incremental/V0001__add_game_order.sql

如果目标表已经存在，不要反复执行初始化 SQL；应检查实际表定义与索引。 应用启动只校验结构，不创建或修改数据库表。历史 config_schema_migrations 仅作遗留记录，新代码不再检查或更新。 参见 数据库说明。

4. Supervisor 管理服务

Supervisor 配置由服务器独立管理，例如 /etc/supervisor/conf.d/middle-platform.conf。以下是配置中心的参考样例，使用前要确认账号存在、权限正确、YAML 已填写、服务已在 8201 监听：

ini
[program:config-center]
command=/data/middle-platform/bin/config-center -config /data/middle-platform/config/config-center.yaml
directory=/data/middle-platform
user=middle-platform
autostart=true
autorestart=unexpected
stopsignal=TERM
stopwaitsecs=40
redirect_stderr=true
stdout_logfile=/data/middle-platform/logs/config-center.log
stdout_logfile_maxbytes=50MB
stdout_logfile_backups=5
environment=CONFIG_GO_ADDR=":8201"

对于 sdk-core-1 / sdk-core-2，可复用 bin/sdk-core 与 config/sdk-core.yaml，但分别配置 SDK_CORE_ADDR=":8211" / ":8212"、独立 [program:...] 名称和日志文件。sdk-service 使用独立的 bin/sdk-service、config/sdk-service.yaml，默认监听 :8221；接入端同理使用独立进程、DSN 与端口。配置变更后：

bash
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status
sudo supervisorctl restart config-center
sudo supervisorctl tail -f config-center

生产机原有 Supervisor 配置应以实际路径、命名和用户为准，不要因为示例而覆盖已有服务定义。如改用 systemd，请配置 Restart=on-failure、KillSignal=SIGTERM、TimeoutStopSec=40s，日志由 journald 收集；两种管理器不要同时控制同一个进程。

5. Nginx 网关与访问边界

以下示例按后端内部路由 /api/... 转发。若公网使用 /sdk/api/...，需在 Nginx 明确移除 /sdk 前缀后再交给后端，避免出现双重前缀。

  • 对外业务域名：/api/core/ 转发到 SDK Core 多实例；/api/service/ 转发到 SDK Service（平台核验/查询/封解禁和游戏事件/订阅消息）。
  • 管理域名或受保护内网：/api/config/ 转发到配置中心，后台静态页来自 admin/；对管理和同步路径设置白名单/认证。
  • /internal/config/callback 只允许配置中心从可信网络访问接入端；验证 HMAC 和时间窗口并不能替代网络边界。
nginx
upstream sdk_core {
    server 127.0.0.1:8211;
    server 127.0.0.1:8212;
}
# 以下 location 仅放在对外 SDK API 对应的 server 中
# 必须放在通用 /api/core/ 路由之前：SDK 管理接口不能通过公开 SDK 网关访问。
location ^~ /api/core/admin/ {
    return 403;
}
location ^~ /api/core/ {
    proxy_pass http://sdk_core;
}
location ^~ /api/service/ {
    proxy_pass http://127.0.0.1:8221;
}

Nginx 不会因 /health/ready 自动从静态 upstream 中摘除后端；需要明确的流量摘除流程或具备主动健康检查的网关。

配置管理前端：运行时配置

前端构建采用 Vite base: './'，可以直接放在 Nginx 的 /admin/ 或其他子路径下。静态资源使用相对路径，不需要修改打包脚本或重新构建。

前端所有配置中心 API 请求从 admin/config.js 中读取：

js
window.__MIDDLE_PLATFORM_CONFIG__ = {
  apiBaseUrl: '/api/config',
  sdkApiBaseUrl: '/api/core'
}

注意：此文件是浏览器能读取的公开配置，不要加入密码、访问令牌或 Webhook 密钥。apiBaseUrl 指向配置中心，sdkApiBaseUrl 指向 SDK Core。管理页面只可通过内网/受认证的独立网关访问，不得通过公开 SDK 网关访问 /api/core/admin/。

为了确保更新 admin/ 静态资源时不覆盖生产配置，建议在正式服务器将配置长期保存于 /data/middle-platform/config/admin.js：

bash
cp -n /data/middle-platform/admin/config.js /data/middle-platform/config/admin.js
vi /data/middle-platform/config/admin.js

在现有的 zk.skybluek.com HTTPS server {} 内，优先配置精确匹配：

nginx
location = /admin/config.js {
    alias /data/middle-platform/config/admin.js;
    add_header Cache-Control "no-store" always;
}
location = /admin {
    return 301 /admin/;
}
location ^~ /admin/ {
    alias /data/middle-platform/admin/;
    index index.html;
    try_files $uri $uri/ /admin/index.html;
}
location ^~ /api/config/ {
    proxy_pass http://127.0.0.1:8201;
}

该规则只演示配置中心相关路径。SDK Core 的 /api/core/ 仍应独立配置负载均衡代理，不能转发到配置中心。此处 proxy_pass 不附加 URI，直接透传原始 /api/config/ 请求路径。

bash
nginx -t && systemctl reload nginx
curl -i https://zk.skybluek.com/admin/config.js

改动 admin.js 后强制刷新浏览器即可生效，不需要重启 Supervisor。原项目使用 hash 路由，子路径刷新不会要求额外的前端路由配置。

安全提醒： 配置中心管理 API 默认启用 adminAuth 请求签名，/admin/ 和 /api/config/admin/ 仍须同时通过 IP 白名单或网关认证保护。只隐藏前端页面不能保护管理接口。

6. 直接发布与失败排查

本项目使用固定的 bin/、admin/、sql/ 目录，不建立 releases/ 版本目录，也不提供自动或手动回滚脚本。发布工具见 本地发布说明。

powershell
# 在开发机上执行：默认打包、上传、更新文件、重启 Supervisor 并验活
.\publish\publish.ps1 -Version v1.0.0

# 仅部署 SDK Core（按 publish.config.json 的 services 配置依次重启）
.\publish\publish.ps1 -Version v1.0.1 -Service sdk-core

# 仅更新文件，不重启
.\publish\publish.ps1 -Version v1.0.2 -SkipRestart
  1. 发布前确认服务与数据库结构兼容。DDL 仍在单独变更窗口由管理员审核并执行，不随脚本自动迁移。
  2. 上传后校验 SHA-256、架构、归档内容、所选服务；校验成功再把文件逐个写入同目录临时文件并重命名替换，保留 config/、logs/、admin/config.js。
  3. 默认读取本地 publish/publish.config.json 的 services（Supervisor 进程名 → 健康检查端口），只重启选中模块对应的实例并逐个验证本机 /health/ready。实例支持 config-center-1/2、sdk-core-1/2/3 等名称；新增实例只需改 JSON。-SkipRestart 可跳过这一阶段。
  4. 单次发布不是跨多个文件的事务；更新、重启或验活失败不会自动回滚，可能需要人工修复。Nginx 静态 upstream 不自动根据健康端点摘流量，两个 Core 顺序重启不保证零中断。
  5. 发布后还需人工抽查充值订单、配置同步和事件上报等关键业务，确认未发生接口或配置不兼容。

7. 日志、停服与排障

四个 Go 进程共用 shared/logging（log/slog），YAML 示例：

yaml
log:
  level: info
  format: json
  output: stdout
  accessEnabled: true
  slowThreshold: 500ms

支持 LOG_LEVEL、LOG_FORMAT、LOG_OUTPUT、LOG_ACCESS_ENABLED、LOG_SLOW_THRESHOLD 环境变量；INSTANCE_ID 可标记实例。HTTP 响应携带 X-Request-ID，访问日志含 service、instance、request_id、status、duration_ms 等字段，不记录密码、签名、请求体。Supervisor 收集 stdout 并轮转；若选择 systemd 则使用 journalctl / journald。不要把高基数的 request_id 用作日志系统标签。

服务接到 SIGINT 或 SIGTERM 时先将 /health/ready 置为不可用，http.Server.Shutdown 等待存量 HTTP 请求（最多 30 秒），再等待 Webhook 或同步 Worker 并关闭数据库连接；超时可能被强制关闭，依靠游标/租约重试恢复。Supervisor 应设置 stopsignal=TERM 和至少 40 秒停机宽限时间。不要使用强制 Kill 作为正常停机方式。

提醒： Go 的 Shutdown 不会自动排空 WebSocket/hijacked 连接；未来 SDK 新增此类连接需单独处理退出。

上线发布前检查

  • 配置中心管理写接口始终注册，默认需要 adminAuth 签名：升级部署前还必须由防火墙、私有网络或具备身份验证的网关限制整个 /api/config/ 前缀，特别是 /api/config/admin/、节点原始 JSON 和同步快照，避免任意用户写入或读取服务端密钥。不要仅隐藏管理网页。
  • SDK Core 订单接口和补偿 Worker 始终加载，数据库必须已有 game_order 表，账号需配置表 SELECT 与订单表 SELECT/INSERT/UPDATE；SDK Service 还需服务开关表与游戏、大区、渠道包的只读权限。
  • 平台 v1 缺少实付金额字段的签名完整性认证；SDK Core 不做二次查单，按签名和登记金额一致性执行支付确认。上线前须核实平台服务端可信定价、支付成功回调保障和游戏幂等发货，并接受现有回调协议的残余风险。
  • 部署前按各模块当前 YAML 模板更新私有配置，删除废弃开关及环境变量；代码合并不代表已经更新 Nginx ACL、线上配置或数据库。

8. 事件上报迁移发布顺序（重要）

  1. 先在存量权威库执行 sql/incremental/V0008__add_sdk_subscribe_message.sql，确认 event_report、subscribe_message 已注册且渠道环境功能开关配置正确。
  2. 把原 /data/middle-platform/config/sdk-core.yaml 中的 platform.eventReportURL 移到 sdk-service.yaml 的同名配置；为订阅消息填写 platform.subscribeMessageURL。Core YAML 中必须删除旧 platform，否则严格 YAML 解码将拒绝启动。
  3. 先验证 Nginx /api/service/ 转发正确，再部署 SDK Service 和 SDK Core 新程序。旧 Core 的 POST /api/core/events/{env} 删除后返回 404。
  4. 同步更新游戏端或调用 SDK 的事件上报 URL 到 POST /api/service/events/{env}，新增订阅消息使用 POST /api/service/subscribe/{env}。
  5. 迁移切换不是无缝兼容：游戏方未更新旧地址时上报会失败。生产发布窗口应协调上游切换，必要时由受控网关短期转发旧路径到新 Service，完成切换后移除，避免双写。

发布不执行 SQL、不自动修改服务器 YAML，也不会自动变更 Nginx；必须按以上顺序人工部署。

SDK 管理接口的 Nginx 隔离

SDK Core 进程中同时存在公开业务路由和 /api/core/admin/ 管理路由。管理路由默认启用 adminAuth 请求签名，但没有用户登录/RBAC。生产环境仍应使用两个受网络隔离的网关入口：

  • 公共 SDK server：如上所示，用 location ^~ /api/core/admin/ { return 403; } 拒绝管理前缀，再代理 /api/core/ 业务。
  • 独立管理 server：仅可信内网、VPN 或带认证的网关可以访问，允许 /api/core/admin/ 反向代理到 sdk_core；后台静态页面及 /api/config/admin/ 也由该入口保护。

确保配置文件中带 /sdk 外部前缀时，先在对应外层 location 显式拒绝 /sdk/api/core/admin/，不能只拦截内部路径。请验证未认证的外部请求无法访问管理接口后才开始切流；单纯隐藏管理页面不足以保障安全。
