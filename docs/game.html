GAME SERVER API

游戏服务端接入文档

提供给游戏开发者的接入协议，覆盖配置查询、充值登记与发货、渠道事件上报及用户核验。

纯 HTML · 无外部依赖基于当前 main 协议整理8 个章节

接入准备

游戏方所需参数、环境与职责

游戏通过 SDK Core 查询配置、登记订单和上报事件；支付成功后由中台向游戏发送发货通知。启用用户核验时，中台 SDK Service 会主动调用游戏提供的用户核验地址。

参数说明
envprod 正式、test 测试、review 提审
appid渠道包的全局唯一编码，例如 110006
gameSecret游戏侧与中台共用签名密钥；仅服务端保存
appSecret平台与中台共用签名密钥；由中台维护，游戏侧不使用

接入配置

  • 中台管理员为游戏配置 game.config.gameSecret，并为渠道包绑定对应环境的区服组。
  • 在大区配置 region.config.payNotifyUrl（支付发货通知地址）和 region.config.userCheckUrl（用户核验地址）。
  • 事件上报、用户核验分别需要启用对应全局开关和渠道包环境开关；未绑定默认关闭。
  • 除特殊游戏协议外，不需要配置适配器；用户核验默认使用 standard。
  • 本文所有中台路由从 /api/ 开始，不含 /sdk。实际域名由部署网关提供。
示例中的域名、AppID、订单号和签名都是演示值；请使用自己的环境和密钥生成真实签名。

查询 SDK 配置

根据环境和渠道包获取映射后的配置
GET/api/core/config/{env}/{appid}

该接口只读，无需请求签名。仅返回当前映射规则配置的公开字段，不会直接下发游戏密钥或平台密钥。

路径参数

参数必填说明
env是prod/test/review
appid是渠道包 AppID

请求示例

HTTP
GET /api/core/config/test/110006 HTTP/1.1
Host: api.example.com

成功响应

JSON
{
  "code": 0,
  "message": "success",
  "data": {
    "snKey": "110006",
    "zoneKey": "s1001",
    "tsKey": "example-key"
  }
}

实际 data 键名来自编译进 SDK Core 的响应映射；路径不存在或值为 null 时可能省略字段。false、0 和空字符串仍保留。

AppID 不存在、环境未绑定，或相关配置节点已停用时通常返回 HTTP 404；参数非法为 400。

登记充值订单

支付前登记游戏订单，支持幂等
POST/api/core/orders/{env}/{appid}

游戏在支付流程中先向 Core 登记订单；登记成功不表示玩家已经付款。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
game_order_idstring是游戏订单号，同 AppID 下跨环境唯一
amountinteger是金额，单位分，必须大于 0
attachstring是透传数据，可以为空字符串

请求示例

HTTP
POST /api/core/orders/test/110006 HTTP/1.1
Host: api.example.com
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 gameSecret 计算的 SHA-1 小写签名>

{"game_order_id":"G100","amount":600,"attach":"roleId=1"}

成功响应

JSON
{
  "code": 0,
  "message": "success",
  "data": {
    "game_order_id": "G100",
    "registration_status": "REGISTERED"
  }
}
  • 签名包含 gameSecret、AppID、时间戳、nonce 和 Body 所有顶层非空值；不包含 env 或 operation。
  • 同一 AppID 下相同参数重复登记为幂等成功；若环境、金额或 attach 不一致，则返回 HTTP 409。
  • 平台支付回调由 Core 接收，游戏端不要直接请求平台支付回调路由。
订单号必须能稳定关联游戏内的角色、区服和订单记录；不能把 REGISTERED 当成发货依据。

接收充值发货通知

SDK Core 向游戏的固定通知地址 POST
POST{region.config.payNotifyUrl}

支付平台通知 Core 成功且订单校验通过后，Core 异步向登记时保存的 payNotifyUrl 发货。此地址由游戏方提供，不是中台固定 API 路径。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型说明
order_nostring平台订单号
game_order_idstring游戏订单号
amountinteger支付金额，单位分
attachstring登记时的透传数据
paid_atstring支付完成时间

通知示例

HTTP
POST /pay/notify HTTP/1.1
Host: game.example.com
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 gameSecret 计算的 SHA-1 小写签名>

{"order_no":"P100","game_order_id":"G100","amount":600,"attach":"roleId=1","paid_at":"2026-11-03T00:00:00Z"}

成功响应（必须严格一致）

HTTP
HTTP/1.1 200 OK
Content-Type: text/plain

0123456789abcdef
  • 先验签并检查请求时间戳、AppID、订单号、金额、支付状态以及本地订单环境，再在事务中完成幂等发货。
  • 只有 HTTP 200 且响应体为本次 x-nonce 原始字符串才视为成功；不能添加 JSON、引号、空格或换行。
  • HTTP 非 200、超时或 nonce 不匹配会触发 Core 持久化重试；通知可能重复到达。
  • 签名中包含 Body 所有顶层非空值，不签 env、operation。
发货必须幂等：建议基于 game_order_id 建唯一约束，订单状态与道具/货币发放在同一事务中完成。

上报渠道事件

游戏统一上报 Core，再转发至渠道平台
POST/api/core/events/{env}

仅支持已绑定环境的渠道包事件，AppID 放在 x-app-id Header，而不是 URL 中。不支持无 AppID 的区服事件。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
eventstring是事件名；非空，最长 128 字节
extobject是非空 JSON 对象，存放渠道业务字段

请求示例

HTTP
POST /api/core/events/test HTTP/1.1
Host: api.example.com
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 gameSecret 计算的 SHA-1 小写签名>

{"event":"login","ext":{"areaId":"1","openId":"user123","roleId":"45940775","roleLevel":80}}

成功响应

JSON
{
  "code": 0,
  "message": "success",
  "data": true
}
  • 请求体只允许 event、ext 两个顶层字段；最大 64 KiB，不允许重复键。
  • 签名包含 Body 的 event 字符串及 ext 紧凑 JSON 文本，序列化时要保持字段顺序与格式一致。
  • 全局 event_report 和渠道环境开关必须均为启用；未绑定时默认关闭。
  • Core 同步转发平台，超时 5 秒；现阶段不持久化事件、不自动重试，失败可由游戏侧决定重试。
事件上报请求失败并不一定代表平台未处理；重试可能导致重复事件，重要事件应建立业务幂等键。

实现用户核验接口

SDK Service 主动调用游戏侧标准适配器协议
POST{region.config.userCheckUrl}

游戏方提供 region.config.userCheckUrl，由 SDK Service 发起 POST。默认适配器 standard 无需设置，只有特殊游戏协议才设置自定义适配器。

请求 Header

Header格式/说明
Content-Typeapplication/json，仅 JSON POST 请求
x-app-id渠道包 AppID（与 URL 中 AppID 必须匹配，若 URL 含 AppID）
x-timestampUnix 秒时间戳，允许前后 5 分钟
x-nonce8 字节随机数的小写十六进制，恰好 16 位
x-signatureSHA-1 小写十六进制，恰好 40 位

请求 Body

字段类型必填说明
open_idstring是待核验的平台用户标识

请求示例

HTTP
POST /internal/user/check HTTP/1.1
Host: game.example.com
Content-Type: application/json
x-app-id: 110006
x-timestamp: 1793700000
x-nonce: 0123456789abcdef
x-signature: <使用 gameSecret 计算的 SHA-1 小写签名>

{"open_id":"user123"}

用户存在

JSON
{
  "code": 0,
  "data": {
    "exists": true
  }
}

用户不存在

JSON
{
  "code": 0,
  "data": {
    "exists": false
  }
}
  • 签名包含 gameSecret + appId + timestamp + nonce + open_id，按字符串值排序、下划线拼接后 SHA-1 小写。
  • 严格要求游戏返回 HTTP 200、code=0、data.exists 为布尔值。
  • 网络故障、超时或无效响应属于调用失败，不能用 exists=false 代替。
这里的用户核验是 Core/Service → 游戏；平台 → Service 的调用规则见平台文档。

游戏侧签名规则

订单、事件和游戏接收回调采用统一 SHA-1

参与签名的值

来源值
服务端密钥gameSecret 原始 UTF-8 字符串
Headerx-app-id、x-timestamp、x-nonce
BodyJSON 顶层全部非空值；对象或数组整体转成紧凑 JSON 文本
  • 过滤 null 和空字符串；数字 0、布尔 false 仍参加。
  • 把所有参与签名的值转成字符串，按值进行字典序升序排序，用下划线 _ 拼接。
  • 对拼接结果计算 SHA-1，输出 40 位小写 hex；不额外加前后缀。
  • 不签字段名、URL、HTTP 方法、环境 env 或操作名 operation。

已校验的签名样本

签名前字符串
0123456789abcdef_110006_1793700000_600_G100_测试-密钥!
SHA-1 输出
a8c30a586539b1d9cd7c5429421e3e88b6a02f6e

Java 17+ 签名工具

Java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.ArrayList;
import java.util.Collection;
import java.util.HexFormat;
import java.util.List;

public final class SdkSignature {
    private static final SecureRandom RANDOM = new SecureRandom();

    private SdkSignature() {}

    public static String nonce() {
        byte[] bytes = new byte[8];
        RANDOM.nextBytes(bytes);
        return HexFormat.of().formatHex(bytes);
    }

    public static String sign(
            String secret, String appId, String timestamp, String nonce,
            Collection<String> bodyValues) throws Exception {
        List<String> values = new ArrayList<>(List.of(secret, appId, timestamp, nonce));
        values.addAll(bodyValues);
        values.removeIf(value -> value == null || value.isEmpty());
        values.sort(String::compareTo);
        String plain = String.join("_", values);
        byte[] digest = MessageDigest.getInstance("SHA-1")
                .digest(plain.getBytes(StandardCharsets.UTF_8));
        return HexFormat.of().formatHex(digest);
    }
    // 调用示例：attach 为空，不参与签名
    public static String example(String gameSecret, String timestamp, String nonce)
            throws Exception {
        return sign(gameSecret, "110006", timestamp, nonce, List.of("G100", "600"));
    }
}
这是为兼容现有平台协议采用的 SHA-1 拼接签名，不是 HMAC。生产应使用 HTTPS、高强度密钥，并独立校验环境、订单归属、权限与业务幂等。

错误处理与联调

常见 HTTP 错误和接入检查
HTTP 状态一般含义
400请求格式、字段或路径参数不合法
401签名或鉴权失败
403功能未启用或无权访问
404AppID 不存在、环境未绑定或路由无效
409订单重复登记但参数不一致等业务冲突
422密钥或业务配置不合法（适用于部分接口）
502/504调用上游失败或超时
503依赖服务或必要配置不可用

最小联调检查

  • 配置查询：分别测试有效 AppID、未绑定环境与不存在的 AppID。
  • 订单登记：测试首次成功、完全相同重复登记、金额冲突，以及签名错误。
  • 充值回调：测试正确验签、精确 nonce 应答、重复通知仅发货一次。
  • 事件上报：测试功能开关、平台返回错误、网络超时。
  • 用户核验：测试 exists=true/false，及上游异常不能误判为不存在。
不保证所有服务的错误响应都使用相同业务 code；应先处理 HTTP 状态，再解析具体响应。
